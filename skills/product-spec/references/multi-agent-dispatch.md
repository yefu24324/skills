# 多 Agent 自动派发协议

协议版本：`1.0`

## 目标

利用多个 subagent 并行调查不同证据面和方案面，提高愿望式需求的广度、独立性和速度。并行层只负责只读探索与候选提案；Orchestrator 统一产品模型和人类交互，Author 唯一写入正式 PRD，Reviewer 使用未参与调查或编写的全新 context 独立审阅。

多 Agent 不是必经仪式。只有独立子任务可以并行、合并收益高于协调成本，且运行环境提供 subagent 能力时才自动派发。

## 复杂度路由

在 `DISCOVERY` 开始时评估以下信号：

- 输入是否愿望化或目标范围尚未成形；
- 是否涉及多个角色、核心对象或权限边界；
- 是否跨越三个及以上页面或两个及以上主流程；
- 是否需要多个标杆产品或跨领域交互对比；
- 是否包含生命周期、审批、金额、删除、合规或外部集成；
- 仓库证据是否分散在多个独立模块；
- 是否属于新产品、重大重构或 `REWRITE`。

按以下档位派发：

| 档位 | 典型任务 | 自动派发 |
| --- | --- | --- |
| `SIMPLE` | 单页面文案、局部字段、明确的小改动 | 不派发；主 Agent 直接调查 |
| `STANDARD` | 一个普通能力、2～3 个页面、需要一次竞品对比 | 派发 2 个探索 subagent |
| `COMPLEX` | 跨页面流程、多角色或生命周期、愿望式新能力 | 派发 3～4 个探索 subagent |
| `PROGRAM` | 新产品或多个可独立能力域 | 先按能力域分波次派发；每波最多 4 个并发探索角色 |

若只有一个可用 subagent 槽位、任务不能安全拆分，或派发成本明显高于收益，降低档位并记录原因。不要为了满足数量而创建重复角色。

## 可选探索角色

根据任务选择互补角色，不要求每次全部使用：

### 项目证据调查员

调查当前文档、代码、测试、术语和历史决策，返回当前行为、约束、冲突与未知项。只读，不修改仓库。

### 直接标杆研究员

研究 1～2 个直接同类知名产品的完整用户任务和对象模型，记录依据等级、时效、可迁移原则与不适用部分。

### 跨领域交互研究员

研究因某项交互体验出色而知名的相邻产品，提供不同于直接竞品的方案，避免同类产品之间互相复制形成的盲点。

### 业务模型分析员

推导角色、权限、业务对象、归属、生命周期、规则和高风险决定，识别必须由人类确认的边界。

### 流程与异常分析员

推导主流程、重要分支、失败、取消、撤销、重试、冲突和恢复；检查业务状态迁移是否闭环。

### 页面体验分析员

提出页面地图、页面职责、导航、Section 关系、渐进披露和高频效率路径。只产出候选结构，不写正式页面规格。

通常优先组合：

- `STANDARD`：项目证据调查员 + 标杆研究员；
- `COMPLEX`：项目证据调查员 + 直接标杆研究员 + 业务/流程分析员 + 页面体验分析员；
- 当前项目证据很少时：两个使用不同样本的标杆研究员 + 业务模型分析员；
- 后台或强流程产品：项目证据调查员 + 业务模型分析员 + 流程异常分析员 + 页面体验分析员。

## 派发输入契约

每个 subagent 只接收完成自身任务所需的最小上下文：

- 任务目标和明确范围；
- 当前用户愿望或产品问题；
- 与角色相关的证据路径或可用资料；
- 必须遵守的产品约束和中文输出要求；
- 指定的研究样本或独立研究方向；
- 只读边界和禁止修改正式 PRD；
- 标准输出契约。

不要把 Orchestrator 的预期结论、推荐答案或其他 subagent 的结论提前泄漏给独立探索角色。需要对照验证时，让不同 subagent 独立得出结论。

## 探索输出契约

每个 subagent 返回一份 `ExplorationReport`：

1. `report_id`：`EXP-*`；
2. `role`、`scope`、`agent_context`；
3. `sources`：来源、访问日期和依据等级；
4. `confirmed_findings`：已确认项目事实；
5. `interaction_patterns`：可迁移原则及适用原因；
6. `gaps`：从愿望到可实施规格缺少的内容；
7. `options`：候选方案、推荐和取舍；
8. `affected_entities`：角色、对象、流程、页面、规则和验收；
9. `suggested_records`：建议的 `BM-*`、`PROP-*`、`CLAR-*`；
10. `risks_and_unknowns`：风险、冲突、未验证信息和时效限制；
11. `non_applicable_ideas`：明确不适合当前场景的竞品复杂度；
12. `confidence`：`HIGH`、`MEDIUM` 或 `LOW`，并说明原因。

禁止只返回一份完整 PRD。禁止直接创建、修改或批准正式 revision。

## 并行与波次

第一波并行调查相互独立的证据面，不让 subagent 彼此等待。Orchestrator 收齐输出后再决定是否需要第二波定向验证。

只有出现以下情况才启动第二波：

- 多个报告在高影响事实上冲突；
- 标杆结论依据等级低但会影响核心方案；
- 仍有明显需求缺口且无法通过已有证据解决；
- 人类选择了需要进一步验证的候选方向。

第二波只验证具体争议，不重新做一遍完整调查。默认探索总轮次不超过两波；需要更多轮次时先向人类说明原因和预期收益。

## 汇总与冲突仲裁

Orchestrator 不能直接拼接报告。按以下顺序合并：

1. 按来源和依据等级区分事实、范式与假设；
2. 以项目权威证据覆盖通用竞品类比；
3. 将同义对象、流程和页面统一到一个稳定 ID；
4. 合并重复缺口和方案，保留真实分歧与取舍；
5. 对高影响冲突创建 `CLAR-*`，不得用多数投票决定；
6. 将可迁移原则转成 `BM-*`，候选方案转成 `PROP-*`；
7. 向人类呈现统一的决策包，不展示互相矛盾的原始 PRD 拼盘。

subagent 的一致意见也不自动成为事实；仍需检查来源质量与产品适配性。

## 写入与独立性边界

- 探索 subagent：只读，不写正式 PRD，不给 verdict。
- Orchestrator：写阶段记录、ExplorationReport 汇总、Benchmark、Proposal、Clarification 和 handoff；不写正式 revision。
- Author：在所有适用确认完成后唯一写正式 revision；不得机械合并探索报告。
- Reviewer：必须使用未参与探索、汇总或 Author 编写的全新 agent context；不得把探索 subagent 复用为最终 Reviewer。

Reviewer 尚未创建时，在 DispatchRecord 中将 `reviewer_context` 写为 `RESERVED_NEW_CONTEXT`。启动最终审阅后回填实际 context 标识，并验证它不在探索、Orchestrator 或 Author context 集合中。

并发 subagent 不得编辑同一文件。确需保存原始报告时，由 Orchestrator 统一写入 `docs/product/research/`，或为每个报告分配独立且无重叠的文件。

## 失败与降级

- 某个探索 subagent 失败：其余结果仍可使用；Orchestrator 判断是否重试或自行补齐。
- 输出偏离范围或缺少证据：丢弃低质量部分，不为凑齐报告而采纳。
- 环境不支持 subagent：由主 Agent 串行执行同一调查职责，并在 handoff 中标记未并行。
- 可用并发槽位少于计划：优先保留项目证据、直接标杆和高风险业务分析，其他角色串行完成。
- 人类在探索中给出新方向：停止过时分支，重新计算影响，避免继续消耗在已否决方案上。

自动派发不得扩大用户授权范围，不得写生产系统、发送外部消息或执行与产品研究无关的变更。

## 派发完成门禁

进入人类确认前，Orchestrator 必须能回答：

- 每个 subagent 为什么需要，是否与其他角色互补；
- 每个关键结论来自何种证据等级；
- 报告间冲突如何解决或升级；
- 哪些竞品思路明确不适用；
- 哪些 `PROP-*` 可以由 Agent 补全，哪些必须由人类确认；
- 是否仍保留一个统一产品模型、一个正式 Author 和一个全新 Reviewer。
