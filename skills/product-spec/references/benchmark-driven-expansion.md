# 标杆产品对比与主动扩写

方法版本：`1.0`

## 目标

把“做一个某类产品”“加一个管理功能”等愿望式输入，扩写成可供人类选择和修正的产品方案。Agent 负责研究、类比、提出候选结构和补齐常见缺口；人类负责确认产品价值与关键取舍，无需从零描述每个页面。

标杆产品是启发和对比材料，不是需求来源。借鉴可迁移的交互原则，不复制品牌界面、专有文案或与当前场景不匹配的功能。

## 先识别产品原型

根据目标用户、核心任务、业务对象和使用频率，判断当前能力接近哪些产品原型，例如：

- 项目与工作项管理；
- 文档与知识协作；
- 即时通信与社区；
- 内容创作与多人编辑；
- 电商、交易或运营后台；
- 市场平台与预订；
- 开发协作与审批流；
- 数据分析与监控；
- 客户关系或工单管理。

同一产品可以组合多个原型。不要仅凭行业名称选择标杆，应优先匹配用户任务、对象关系和交互密度。

## 选择对比样本

每个关键能力选择 2～4 个高相关样本：

1. 一个直接同类产品，用于比较完整工作流；
2. 一个公认擅长目标交互的产品，用于提炼交互范式；
3. 必要时选择一个相邻领域产品，用于寻找不同解法；
4. 存在明显风险时，可加入一个反例说明不采用的模式。

示例路由仅用于帮助选样，不代表这些产品当前版本必然采用某项设计：

| 产品原型 | 可考虑的知名样本 |
| --- | --- |
| 工作项与项目管理 | Linear、Jira、Asana、Trello |
| 文档与知识协作 | Notion、Confluence、Google Docs |
| 通信与社区 | Slack、Microsoft Teams、Discord |
| 内容创作与协同 | Figma、Canva、Miro |
| 交易与运营后台 | Stripe、Shopify |
| 市场与预订 | Airbnb、Booking.com |
| 开发协作与审批 | GitHub、GitLab |

不要总选最知名的产品；若它的用户规模、业务约束或操作频率与当前场景不同，应降低参考权重。

## 标注依据与时效

对产品交互的描述必须标明依据等级：

- `CURRENT_VERIFIED`：本次通过官方资料或可访问的当前产品验证；可以描述为当前行为，并记录来源与日期。
- `PROJECT_EVIDENCE`：来自当前项目材料；可以作为当前项目事实。
- `KNOWN_PATTERN`：来自模型对知名产品的已有知识，可能过时；只能表达为“已知范式”或“候选借鉴”，不能声称是产品当前行为。
- `HYPOTHESIS`：为探索而提出的类比；必须等待人类确认。

当工具允许且某项对比会影响重要产品决定时，优先核实官方帮助文档、官方产品说明或当前可访问界面。无法核实时保留时效声明，不因缺少实时资料停止提出候选方案。

## 提炼交互范式

不要停留在“像某产品”。从样本中提炼以下适用维度：

- 信息架构：核心对象如何分组、嵌套和关联；
- 导航与定位：用户如何进入、返回、切换上下文；
- 创建与首次使用：如何降低空白页和配置成本；
- 浏览、搜索与筛选：高频对象如何被找到；
- 查看与编辑：详情页、抽屉、内联编辑或分步表单如何取舍；
- 状态与反馈：保存、提交、处理中、成功和失败如何反馈；
- 批量与效率：高频用户如何减少重复操作；
- 协作与权限：评论、通知、分享、审批和可见性如何工作；
- 异常恢复：取消、撤销、重试、冲突和恢复如何处理；
- 渐进披露：简单用户与高级用户如何共用同一能力。

只分析当前任务适用的维度，不为追求完整而强行增加功能。

## 从对比生成提案

每个主动扩写项使用 `PROP-*` 记录：

- `gap`：用户愿望与可实施规格之间缺少什么；
- `user_job`：需要支持的用户任务；
- `benchmarks`：参考的 `BM-*` 及依据等级；
- `options`：通常给出 2～3 个可行方案；
- `recommended_option`：推荐方案及适用原因；
- `transferable_principle`：真正借鉴的交互原则；
- `tradeoffs`：效率、学习成本、复杂度、权限或扩展性的代价；
- `affected_entities`：受影响的角色、对象、流程、页面、规则和验收；
- `decision_owner`：Agent 可补全、Author 可推导或 Human 必须决定；
- `status`：`PROPOSED`、`ACCEPTED`、`MODIFIED`、`REJECTED` 或 `DEFERRED`。

提案应写成“当前问题 → 标杆解法的原则 → 当前场景方案 → 取舍 → 需要人类确认的决定”，而不是堆砌竞品功能列表。

## 分阶段与人类确认

复杂任务至少设置以下确认点；小任务可以合并，但不能跳过所有交互直接生成最终 PRD：

1. **意图与范围**：确认用户、问题、期望结果、首期范围和非目标；
2. **标杆与方向**：展示选择的样本、可迁移原则和不适用部分，让人类修正参考方向；
3. **对象与流程**：确认核心对象、生命周期、权限、主流程和重要分支；
4. **页面地图**：由 Agent 主动提出页面、职责、导航和关键交互，再由人类确认；
5. **边界与验收**：确认异常、删除、恢复、通知、审计、性能期望和验收结果中影响较高的内容。

每轮优先发送 3～5 个“决策包”。每个决策包包含推荐方案、备选方案、依据、取舍和影响范围。先展示已经推导或扩写的内容，再请人类选择或修正；不要让人类从空白开始逐页描述。

人类确认后，立即总结已接受、修改、拒绝和仍开放的 `PROP-*`，说明产品模型发生了什么变化，再进入下一轮。不要重复询问已经确认的决定。

## 自主权限边界

Agent 可以直接补全并交给 Reviewer 检查：

- 稳定 ID、追踪关系和文档拆分；
- 从已确认流程直接推导的页面入口、退出和导航闭环；
- 适用的加载、空、错误、成功、禁用和无权限状态；
- 与已确认规则直接对应的反馈、失败恢复和可测试验收候选；
- 不改变产品价值和业务边界的结构性细节。

以下内容必须由人类确认：

- 产品目标、范围、商业模式和成功标准；
- 新角色、权限或数据可见性；
- 核心对象的归属与生命周期；
- 金额、计费、退款、删除、保留、合规和外部承诺；
- 主流程的价值取舍；
- 会改变页面主要职责或导航模型的选择；
- 引入标杆产品能力但当前需求没有业务依据的提案。

## 防止错误借鉴

- 不因知名产品拥有某功能就默认当前产品也需要。
- 不用品牌名代替具体产品行为和验收标准。
- 不复制受到不同规模、监管、商业模式或组织结构驱动的复杂度。
- 不把 `KNOWN_PATTERN` 写成已经核实的竞品现状。
- 不把人类尚未确认的 `PROP-*` 写入正式需求。
- 不一次提出完整竞品功能全集；优先解决当前用户任务的最高价值缺口。
