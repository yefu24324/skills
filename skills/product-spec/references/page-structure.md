# 页面结构规范

规范版本：`4.0`

## 目标

页面规格首先服务于产品、设计、开发和测试人员阅读。读者不需要查阅代号表，也应能直接理解页面解决什么问题、包含哪些功能、用户如何操作以及操作后发生什么。

每个用户可见页面都必须同时提供：

- 页面用途与使用场景；
- 用户可以完成的主要任务；
- 使用组件树表达的页面结构；
- 各功能区域的内容、操作和结果；
- 重要状态、权限限制与失败恢复；
- 与相关流程、规则和其他页面的中文链接。

非可视能力明确说明其产品行为和用户可观察结果，不为其虚构页面结构。

## 页面概述

在结构图之前，先用连续、自然的中文说明：

- **页面用途**：页面为谁解决什么问题，不使用“承载某能力”代替真实用途；
- **使用场景**：用户从哪里进入，通常在什么情况下使用；
- **主要任务**：用户可以在这里查看、创建、修改、确认或完成什么；
- **完成结果**：操作成功后产生什么业务结果，用户接下来可以去哪里。

页面概述必须能让第一次接触产品的读者独立理解页面职责。不能只写一句抽象的“主要职责”，再要求读者到能力、规则或流程文件中拼接页面功能。

## 组件树格式

每个用户可见页面使用结构化文本树表达主要信息结构。每个节点严格使用以下格式：

```text
[PascalCaseComponent] <中文用途>
```

- 方括号内使用大驼峰英文组件名称，例如 `Page`、`Header`、`Input`、`Select`、`Table`、`Button`、`Tabs`、`Editor`、`Drawer`、`Dialog`、`Alert`。
- 尖括号内使用简短、明确的中文，说明该组件在当前页面中的内容或用途。
- 一个节点只使用一个组件名称，不在方括号内加入 ID、缩写、状态或多个单词标签。
- 组件名称表达产品层面的界面类型，不绑定具体前端框架或组件库。
- 没有合适的具体组件时使用 `Section`、`Group`、`List` 等通用名称，不发明难以理解的英文缩写。

示例：

```text
[Page] <工作项列表页>
├─ [Header] <页面标题与工作项数量>
│  └─ [Button] <新建工作项>
├─ [Section] <筛选与搜索>
│  ├─ [Input] <按名称搜索工作项>
│  ├─ [Select] <按负责人筛选>
│  └─ [Button] <清除筛选条件>
├─ [Table] <工作项列表>
│  ├─ [Column] <名称与当前状态>
│  ├─ [Column] <负责人和更新时间>
│  └─ [Button] <查看工作项详情>
├─ [Pagination] <切换列表页码>
├─ [Alert] <加载或操作结果反馈>
└─ [Drawer] <工作项详情>
   ├─ [DescriptionList] <工作项完整信息>
   └─ [Button] <关闭详情>
```

树形符号统一使用 `├─`、`└─` 和 `│ `。组件树表达上下顺序、并列、嵌套和浮层归属，不表达像素尺寸、间距或响应式断点。

## 组件选择

优先使用读者熟悉、含义明确的组件名称：

| 组件名称 | 适用含义 |
| --- | --- |
| `Page` | 页面根节点 |
| `Header` | 页面标题、摘要和页面级主要操作 |
| `Section` | 具有独立产品职责的功能区域 |
| `Group` | 一组紧密相关的信息或操作 |
| `Input` / `Textarea` | 单行或多行输入 |
| `Select` / `Checkbox` / `RadioGroup` | 选择条件或选项 |
| `Tabs` | 在同一上下文内切换内容 |
| `List` / `Table` / `Tree` | 列表、表格或层级数据 |
| `Editor` | 配置、文本或其他内容编辑 |
| `Button` / `Link` | 操作或页面跳转 |
| `Pagination` | 分页控制 |
| `Drawer` / `Dialog` / `Popover` | 抽屉、弹窗或临时浮层 |
| `Alert` / `EmptyState` / `Skeleton` | 结果反馈、空状态或加载状态 |

该表不是封闭清单。可以使用其他通用组件名称，但必须保持大驼峰英文，并让中文用途承担具体产品语义。

## 功能区域说明

组件树之后，按页面中的自然中文区域名称分别说明功能。每个主要功能区域至少回答：

- **用途**：为什么需要这个区域，它帮助用户完成什么；
- **展示内容**：用户可以看到哪些业务信息，关键字段分别代表什么；
- **用户操作**：用户可以执行哪些操作，操作在什么条件下可用；
- **操作结果**：操作成功后数据、页面区域或业务状态如何变化，是否跳转或打开浮层；
- **权限限制**：哪些角色可见、可编辑、可确认或只能查看；
- **状态与恢复**：加载、空数据、校验失败、提交失败、禁用或无权限时如何表现，用户如何继续。

根据页面复杂度使用短段落或表格，但不能只罗列组件名称、按钮名称或追踪关系。简单区域可以合并说明；复杂区域应使用独立三级标题，使读者能够快速定位。

## 交互关系

组件树难以表达的跨区域更新、页面跳转、抽屉或弹窗行为，使用简短中文说明。例如：

- 应用筛选条件后，只刷新“工作项列表”，保留当前搜索条件。
- 选择一条工作项后，在页面右侧打开“工作项详情”，关闭后保留原列表位置。
- 创建成功后关闭“新建工作项”弹窗，将新工作项加入列表并显示成功反馈。

交互说明直接引用中文区域或操作名称。不要另建由英文关系词和内部代号组成的关系树。

## 人类可读的追踪方式

- 正文使用稳定的中文页面名、功能区域名、规则名和流程名。
- 跨文件关系使用指向实际规格文件中文标题的 Markdown 链接，例如以“发布前遵守[编辑与发布分离]”作为链接文字；不要在链接文字中只写规则编号。
- 同一名称在目录、页面标题、流程和链接中保持一致，避免同义词漂移。
- 如果外部系统已有必须保留的编号，可在标题或附录中同时标明并解释；不得让编号代替中文含义。
- 不在正式需求正文、组件树或功能说明中生成 `SEC-*`、`ACT-*`、`PAGE-*`、`CAP-*` 等供 Agent 自己追踪的编码。

## 边界

组件树表达产品层面的信息架构和交互关系，不是视觉设计稿。除非视觉属性本身属于功能、合规或可访问性要求，不规定颜色、字体、精确尺寸、间距、装饰风格、动画参数、响应式断点或具体组件库实现。

## 阻塞条件

以下任一情况都会使页面规格不可通过：

- 第一次接触产品的读者无法从当前文件理解页面用途和主要任务；
- 用户可见页面缺少组件树，或节点没有使用 `[大驼峰英文组件] <中文用途>` 格式；
- 正文使用未解释的内部代号，要求读者查表才能理解页面、区域、操作、规则或流程；
- 只列出区域或按钮名称，没有说明展示内容、用户操作和操作结果；
- 主要区域的顺序、并列、嵌套或浮层关系无法理解；
- 主要操作无法定位到具体功能区域；
- 跨区域更新、页面跳转或浮层行为没有用中文说明；
- 重要状态没有说明影响范围、用户反馈或恢复方式；
- 页面描述与流程、权限、对象状态、共享规则或验收结果相互矛盾。
