# 优秀产品规格质量门禁

门禁版本：`1.0`

## 原则

优秀 PRD 不是最长、页面最多或对标产品最多的文档，而是让产品价值、业务取舍、用户行为和验收结果足够清楚，使设计、开发和测试无需猜测关键产品决定。

质量门禁采用“关键项全部通过”，不使用可以用低价值内容刷高的平均分。

## 一、价值与范围门禁

- 明确目标用户、真实问题和期望结果，而非只写要开发的功能。
- 首期范围能够形成可使用的闭环，非目标和延期内容明确。
- 成功信号能够观察，并与产品目标相对应。
- 每项重要能力都说明为何需要；不能仅因标杆产品拥有就加入。
- 复杂度与当前用户规模、使用频率、业务风险和组织能力相匹配。

## 二、标杆适配门禁

- 标杆样本与当前用户任务、对象关系或交互密度相关。
- 至少比较两个合理方案；没有真正替代方案时说明原因。
- 记录依据等级、来源时效、可迁移原则和不适用部分。
- 推荐结论说明为何适合当前场景，而非只评价竞品“体验好”。
- 正式需求脱离品牌名后仍可独立理解、实现和验收。

## 三、业务模型门禁

- 角色、权限和数据可见性没有相互矛盾。
- 核心业务对象具有明确含义、归属、关系和生命周期。
- 每个状态的进入条件、允许迁移和可见行为明确。
- 共享规则只有一个权威定义，金额、删除、保留、合规等高风险规则已经人类确认。
- 产品对象和规则使用业务语言，不被数据库或组件结构主导。

## 四、流程闭环门禁

- 每项能力具有明确触发、前置条件、主要步骤和完成结果。
- 正常路径、重要分支、失败路径、取消和恢复按适用场景定义。
- 跨页面流程能够追踪到具体页面、Action、对象变化和规则。
- 用户始终知道系统正在做什么、发生了什么以及下一步能做什么。
- 高频任务的步骤和上下文切换经过合理化，没有照搬低频企业流程的复杂度。

## 五、页面与交互门禁

- 页面地图覆盖主流程，每个页面只有一个清晰的主要职责。
- 用户可见页面具有可理解的 ASCII 结构，并与 Section 表一致。
- 主要操作、对象上下文、导航返回和区域更新关系可以定位。
- 加载、空、错误、禁用、成功、无权限和并发冲突按适用场景说明影响区域与恢复动作。
- 复杂度通过默认值、渐进披露、批量操作或快捷路径合理管理，但不为高级功能牺牲首用体验。

## 六、验收与追踪门禁

- 每项重要行为都有可观察、可测试的验收结果。
- 验收覆盖成功、关键失败、权限和状态迁移，不只覆盖理想路径。
- 目标、能力、对象、流程、页面、规则和验收可以双向追踪。
- 不使用“支持”“优化”“智能”“友好”“类似某产品”等无法直接验收的表述替代行为结果。
- 当前 revision、Decision、Clarification、Benchmark、Proposal 和 ReviewRecord 的关系明确。

## 七、人类共识门禁

- 适用的意图、标杆方向、业务模型、页面地图和边界检查点已经与人类交互确认。
- 所有高影响取舍都有明确人类决定，不藏在假设或 Agent 推荐中。
- `REJECTED` 和 `DEFERRED` 提案没有进入当前规格。
- 本轮确认内容、模型变化和剩余开放问题已经反馈给人类。
- 独立 Reviewer 已审阅固定 revision 并给出 `APPROVED`。

## 八、多 Agent 协作门禁

- `SIMPLE`、`STANDARD`、`COMPLEX` 或 `PROGRAM` 档位选择有明确理由。
- 自动派发角色互补，子任务可独立并行，没有为凑数量重复调查。
- 每个 `EXP-*` 具有范围、来源、置信度、风险和不适用方案。
- 报告冲突按证据和人类决定仲裁，实体术语与稳定 ID 已统一。
- 探索 subagent 保持只读，正式 revision 只有一个 Author。
- 最终 Reviewer 是未参与探索、汇总和编写的全新 context。
- 环境不支持 subagent 或任务不适合派发时，记录降级原因；合理不派发不影响质量结论。

## 反向检查：避免过度产品化

即使上述维度都有内容，也要删除以下无业务依据的扩写：

- 只因知名产品存在而加入的功能；
- 首期没有明确用户任务的高级配置；
- 为所有理论异常设计的复杂流程；
- 与当前规模不匹配的权限层级、审批链或管理后台；
- 不能追踪到目标、风险或验收的页面和 Section；
- 重复表达同一规则的说明性段落。
- 多个 subagent 各写一份完整 PRD 后形成的重复与矛盾内容。

Reviewer 应要求删除无依据的范围，而不是把“更多功能”视为更优秀。

## 门禁结论

输出每个门禁的 `PASS`、`BLOCK` 或 `NOT_APPLICABLE` 及证据位置。任何适用门禁为 `BLOCK` 时不得批准；`NOT_APPLICABLE` 必须说明不适用原因。

`CREATE` 和 `REWRITE` 执行全部门禁；`PATCH` 执行受影响门禁及其关系传播范围。若局部变化暴露出目标、权限、生命周期、主流程或页面职责问题，扩大审阅范围，不得机械维持 `PATCH`。
