# 许愿式编程与主动扩写

方法版本：`1.0`

## 触发条件

当用户主要描述期望结果、产品类比或一句功能愿望，而没有给出足以确定产品模型和交互行为的信息时，视为许愿式编程。例如“做一个类似某产品的工具”“加一个项目管理功能”或要求 Agent 自主补齐产品。

新产品、新能力以及明显缺少角色、对象、流程、页面、状态、规则或验收的输入也适用。边界清楚的局部修改和信息充分的规格不强制执行。

## 必须完成的工作

1. 先调查项目中的现有需求、实现、术语和约束，不把标杆产品置于项目证据之上。
2. 识别当前产品原型、核心用户、用户任务和需要补齐的产品缺口。
3. 选择足够且相关的标杆产品或成熟交互范式进行对比。自主决定样本数量和研究深度，只比较与当前任务有关的信息架构、流程、页面职责、操作效率、状态反馈、权限和异常恢复。
4. 记录样本相关性、依据来源与日期、已核实的当前行为、可能过时的已知范式、可迁移原则和不适用部分。重要产品决定依赖某项当前行为时，工具允许则优先核实官方资料或当前界面。
5. 从对比中主动扩写当前输入缺失的产品内容，提出候选方案、推荐方案、取舍和影响范围。不要复制竞品功能清单，也不要因标杆产品具有某项能力就默认当前产品需要。
6. 先向人类展示经过调查的候选模型和推荐理由，再请求确认、修改或拒绝关键提案；不要让人类从空白开始逐页设计。

Agent 自主决定是否使用 subagent、调查分工、确认轮次和产物形式。subagent 只提供证据和候选方案，不并发修改正式规格。

## 记录契约

- `Benchmark`：记录对比样本、相关性、来源与时效、可迁移原则、不适用部分和受影响实体。
- `Proposal`：记录需求缺口、用户任务、候选方案、推荐与取舍、受影响实体、决定归属和状态。
- `Proposal` 状态使用 `Proposed`、`Accepted`、`Modified`、`Rejected` 或 `Deferred`。

只有人类 `Accepted` 或 `Modified` 的高影响 Proposal 才能进入正式规格。Agent 可直接补齐能够由项目证据或已确认产品模型可靠推出的结构性细节，但必须明确依据。

## 人类决定边界

目标、范围、商业模式、角色、权限、数据可见性、核心对象归属与生命周期、主流程价值取舍、页面主要职责或导航、金额、删除、保留、合规和外部承诺必须由人类确认，除非项目权威证据已经明确决定。

## 完成门禁

许愿式输入只有在以下条件满足后才能交给 Author：

- 已完成相关标杆对比，并区分当前证据与可能过时的已知范式；
- 已提出足以补齐关键缺口的候选产品模型，而不是复述用户愿望；
- 高影响 Proposal 已获得人类接受或修改；
- 被拒绝、延期或尚未确认的 Proposal 不会进入正式规格；
- 正式要求能够脱离标杆品牌名称独立理解、实现和验收。
