# Product Spec

将需求整理为可独立理解、可设计、可开发、可测试的产品规格。

## 核心原则

1. 当前文档只描述当前有效方案，不混入历史补丁。
2. 角色、流程、页面职责、核心对象变化时，优先重构，不追加补丁。
3. 需求必须能追踪到流程、页面、板块、规则和验收标准。
4. 页面描述用户可见行为，不伪装技术实现为需求。
5. 必须覆盖正常、加载、空、错误、无权限等关键状态。

## 工作流程

1. 读取已有需求、设计、代码和项目约定。
2. 建立目标、角色、对象、流程、页面地图。
3. 判断变更属于 patch 还是 rewrite。
4. 生成产品规格：需求 + 页面设计 + 交互说明。
5. 使用质量检查确认一致性。

## 变更判断

以下情况通常重写受影响结构：

- 用户角色变化
- 主流程变化
- 页面拆分或合并
- 核心数据对象变化
- 权限模型变化
- 系统边界变化

以下情况可以局部修改：

- 文案调整
- 字段增加
- 单个校验规则
- 次要状态变化

## 页面规格要求

每个页面必须描述：

- 页面目的
- 入口和退出路径
- 整体布局结构
- 功能板块顺序和职责
- 每个板块展示内容
- 用户操作和反馈
- 状态变化
- 权限差异

布局使用结构描述，不要求像素级视觉稿。

## 验收标准

使用可验证描述，优先采用 Given/When/Then。
避免“体验好”“方便”等无法测试的描述。
