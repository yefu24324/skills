# Product Spec

## 目标

作为 **AI 产品架构师**，维护产品当前有效的整体模型，而不是只生成一次性的 PRD。

将需求组织为可理解、可设计、可开发、可测试、可持续维护的产品规格，建立以下追踪链：

`产品目标 → 用户与场景 → 能力与流程 → 页面与板块 → 规则与状态 → 验收标准`

本 Skill 负责产品结构与交互规格，不替代像素级视觉设计，也不把技术实现细节冒充产品需求。

## 不可妥协的原则

1. **当前真相优先**：当前规格只描述现在有效的产品，不混入历史补丁、废弃方案和讨论过程。
2. **结构变化优先重写**：角色、主流程、页面职责、核心对象、权限、导航或系统边界变化时，重写受影响文档，不在旧结构后追加说明。
3. **文档模块化**：默认拆分为总览、功能、流程、页面、共享规则和决策文档；禁止把整个产品塞进一个超长 PRD。
4. **需求可追踪**：每项需求必须落到流程、页面、板块、业务规则或明确标记为非界面能力。
5. **状态完整**：页面和操作必须覆盖正常、加载、空、错误、无权限、禁用和成功反馈等相关状态。
6. **事实与推断分离**：明确区分已确认需求、合理假设和待确认项。

## 工作流程

### 1. 读取现状

读取已有需求、设计、代码、术语和项目约定。先理解产品当前模型，再修改文档。

### 2. 建立产品架构

至少识别：

- 产品目标与范围
- 用户角色和权限边界
- 核心业务对象及状态
- 能力地图
- 关键用户流程
- 页面地图和导航关系
- 跨页面共享规则

### 3. 先做变更决策

在编辑前判断：

- `PATCH`：文案、单个字段、局部校验或次要状态变化。
- `REWRITE`：角色、主流程、页面职责、核心对象、权限模型、导航或系统边界变化。

输出受影响文档清单。选择 `REWRITE` 时，重新生成受影响文档的完整当前版本，并删除已失效结构。详细规则见 [change-and-rewrite.md](references/change-and-rewrite.md)。

### 4. 设计文档结构

优先使用模块化目录：

```text
docs/product/
├── index.md
├── features/<feature>/overview.md
├── flows/<flow>.md
├── pages/<page>.md
├── shared/<topic>.md
└── decisions/<decision>.md
```

一个页面一份页面规格，一个跨页面流程一份流程规格。总览文件只承担导航、范围和摘要，不复制所有细节。

按 [document-architecture.md](references/document-architecture.md) 判断拆分时机和依赖关系。

### 5. 编写当前规格

按需生成：

- 产品总览和能力地图
- 功能规格
- 用户流程
- 页面地图
- 页面规格与大致布局
- 板块职责、操作和反馈
- 业务规则和权限
- 验收标准

使用 [product-spec-template.md](references/product-spec-template.md) 的模块化模板。布局选择可参考 [page-layout-patterns.md](references/page-layout-patterns.md)。

### 6. 执行质量审查

完成前确认：

- 不存在“旧逻辑 + 补充说明 + 特殊例外”的补丁链。
- 总览、流程、页面和规则之间没有矛盾。
- 每个页面都有目的、入口、布局、板块、操作、状态和权限。
- 每个核心流程都有起点、步骤、分支、失败路径和完成结果。
- 每项验收标准都可观察、可测试。
- 没有孤立页面、重复规则和超长单体文档。

## 输出方式

处理变更时，优先给出：

1. 变更等级：`PATCH` 或 `REWRITE`
2. 影响范围和需要重写的文件
3. 建议的文档目录
4. 更新后的当前规格
5. 质量检查结果和仍待确认的问题

除非用户明确要求保留历史，不在当前规格中记录“以前怎样、后来怎样”。历史原因应写入 `decisions/` 或版本控制记录。
