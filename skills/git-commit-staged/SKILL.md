# 提交 Git 暂存区

只根据暂存区生成提交信息。将“分析并展示提交信息”和“实际创建提交”视为两个阶段，未经用户明确确认不得进入第二阶段。

## 1. 检查仓库和暂存区

1. 使用 `git rev-parse --show-toplevel` 确认当前目录属于 Git 仓库。
2. 读取 `git status --short`、`git diff --cached --stat`、`git diff --cached --name-status` 和 `git diff --cached`。
3. 如果没有暂存变更，停止并说明需要先暂存文件。不要自行执行 `git add`。
4. 识别二进制文件、子模块、重命名和删除；不要仅凭 stat 猜测其内容。

提交信息只按本 Skill 定义的规范和当前暂存区内容生成。

不要把未暂存或未跟踪的改动写入提交说明。可以提醒用户这些改动不会包含在本次提交中。

## 2. 生成提交信息

使用以下标题格式：

```text
<type>(<scope>): <subject>
```

- `type` 只能使用 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore` 或 `revert`。
- `scope` 必须填写，根据主要变更所在的包、应用或组件选择一个简短 scope。
- `subject` 使用中文，描述变更目的而不是文件操作，不超过 72 个字符，不以句号结尾。
- 一次提交涉及多个方面时，以主要目的决定 type 和 scope，在正文中概括其余必要信息。
- 只有 diff 能支持时才写正文、`BREAKING CHANGE:` 或 issue footer，不虚构动机、效果、测试结果或关联编号。

正文使用简短的中文条目，并与标题之间保留一个空行。若标题已足够表达完整意图，不添加正文。

## 3. 请求确认

直接展示将要使用的完整提交信息，紧接着向用户使用选项式提问以下选项.

- **提交（推荐）**：按展示的信息创建提交；
- **重新生成**：继续使用交互提问工具收集调整原因，再根据原因重新生成提交信息并重新请求确认；
- **取消**：不执行任何写操作。

不要为确认问题设置自动选择或超时默认值。如果当前环境没有可用的交互提问工具，停止并说明无法完成交互确认；不要退回到要求用户键入“提交”的文本确认方式。

即使用户只显式调用了此 skill，也必须在首次生成后等待确认。用户在原始请求中已经明确给出最终提交信息并明确要求立即提交时，可以把该指令视为确认，但仍需先核对它与暂存内容一致。

## 4. 创建并核验提交

1. 如果确认发生在后续轮次，重新读取暂存区；若内容相较生成信息时发生变化，停止并重新生成，不得提交旧结论。
2. 使用能安全保留多行和特殊字符的 shell 参数或临时 message 文件执行 `git commit`。不要让提交文本被当作 shell 代码解释。
3. 提交失败时原样概括 Git 错误并停止，不通过 `--no-verify` 绕过 hooks，除非用户明确要求且理解影响。
4. 成功后显示 `git log -1 --oneline` 和简要 `git status --short`，报告提交哈希和标题。

不要自动 amend、push 或修改工作区中的其他内容。
